# TIS 本体实践借鉴：0 到 1 实施大纲

## 一、方案定位

本大纲是 [主方案](../2026-08-23-001-refactor-tis-ontology-adoption-plan.md) 的实施导航。目标不是把 TIS 迁入 Data Agent，而是从固定源码快照中抽取可验证的工程模式，经过 Data Agent 的权威、治理、证据与安全边界改造后分阶段落地。

核心判断：

- Data Agent 的本体核心不需要重做；
- 运行时短板主要在“词汇落点之后的受治理召回与关系扩展”；
- 维护侧短板主要在“物理 schema drift 到语义绑定影响”的可审阅闭环；
- TIS 是参考实现，不是新的架构权威。

## 五、关键采用与拒绝

### 采用并改造

- 字典精确匹配 → 发布版本词汇索引；
- 多路召回 → 候选证据，不能单独决定权威路由；
- 图关系展开 → 现有 exact-release relationship read；
- Binding Switch Report → drift-bound semantic impact Candidate；
- Falcon 分层测试 → 现有 release gate / Test Center。

### 明确拒绝

- ObjectType/Property/SemanticRole 替换现有业务主体、维度、指标、公式；
- XML/file store 或 Neo4j 作为权威；
- 通用 `LINKED_TO` 覆盖 typed semantic relationship；
- raw SQL `physicalExpression` 替代 Formula AST；
- PromptSerializer 全量注入 schema/SQL；
- ChatBI 直接生成并执行 SQL；
- LLM 推断自动写入发布语义。

## 六、统一验收原则

每个阶段都必须满足：

1. 先有失败测试，再实现；
2. 绑定 exact workspace/datasource/release/schema snapshot/policy；
3. 相同输入产生相同排序、hash、reason code；
4. Candidate、草稿和陈旧投影不得进入运行时权威；
5. 故障产生 typed fallback，不能隐式读取 latest；
6. 公共投影不含 raw prompt、raw SQL、rows、DSN、provider payload；
7. 完成定向验证后，一个阶段/原子单元一个 scoped commit；
8. 不碰与当前任务无关的脏工作树改动。

## 七、启动条件

用户批准本方案后，仍需在实施前做一次代码基线检查：当前语义架构重构在涉及路径上应有可识别的已提交基线，且文件所有权无冲突。若不满足，先等待或创建独立 worktree；不得把本方案直接叠到来源不明的未提交语义修改上。
