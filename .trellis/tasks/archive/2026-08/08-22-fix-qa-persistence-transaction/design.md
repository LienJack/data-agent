# 技术设计：Q&A 持久化事务与轨迹 schema 修复

## 1. Confirmed causal chain

### Q&A 写入失败

1. Q&A route 冻结 `subagent_catalog_snapshot` 后调用 Effective Config acceptance。
2. `accept_question_run_with_effective_config` 是 `SECURITY DEFINER`，执行身份为 `data_agent_effective_config_rpc_owner`。
3. 函数在写入前调用 security-invoker validator `subagent_catalog_snapshot_is_valid(jsonb,text)`。
4. 10696 撤销了 `PUBLIC` 权限，但未向 Effective Config owner 授予 validator 的 `EXECUTE`。
5. PostgreSQL 抛出 `42501 permission denied`；`withAppTransaction` 回滚并映射为公开 `PERSISTENCE_TRANSACTION_FAILED`。
6. 因为失败发生在原子 acceptance 的校验阶段，数据库没有留下本次 Run 的半成品。

### 页面轨迹轮询失败

1. Content-first Resolution Trace projector 查询 `runs.active_attempt_id`。
2. 持久化模型把 `active_attempt_id` 存在 `outbox`，而当前活动尝试的直接权威是 `run_attempts.status = 'ACTIVE'`；`runs` 从未拥有该列。
3. PostgreSQL 抛出 undefined column，页面轮询反复失败。
4. 同一批代码还切换到 10697 的 v2 Team RPC；本地数据库未应用 10697，因此产生 undefined function。

### Migration drift

1. 10696 于 12:34 应用并登记 checksum `8e74...`。
2. 13:48 的代码修复原地修改了 10696 source/generated migration，生成新 checksum `853f...`。
3. 14:46 新增 10697，但 15:03 启动的 Web 进程未重新完成 migration gate。
4. 当前 `dev:migrate` 会先在 10696 失败，无法继续应用 10697。

## 2. Chosen design

### 2.1 Restore immutable 10696

- 将 `migration-sources/10696` 与生成的 10696 SQL 恢复为已登记 bytes。
- 保留 renderer；`--verify` 必须产生 ledger 中的旧 checksum。
- 不修改 `platform.migration_ledger`。

### 2.2 Add 10698 forward repair

新增 `20260725010698_app_data_agent_subagent_harness_runtime_repair.sql`，以 10697 为 baseline：

1. PostgreSQL 17、executor、baseline ledger、10696 old checksum preflight。
2. 获取 app migration advisory lock。
3. `CREATE OR REPLACE`/受控 definition patch 前向交付 13:48 后原本错误塞回 10696 的行为：
   - `list_agent_profile_revisions_v2` 排除 disabled/revoked Skill；
   - Root Harness v3 payload 加入并校验 `visible_message_refs`；
   - acceptance 构造 `visible_message_refs=[event_id]`。
4. `REVOKE ALL` 后只向 `data_agent_effective_config_rpc_owner` 精确授权 validator `EXECUTE`；保留 validator owner 为 `data_agent_u19_team_owner`。
5. postcondition 同时验证：旧 10696 checksum、函数定义片段、Effective Config owner allow、PUBLIC/backend deny。
6. 登记新的固定 checksum。

不采用“直接 GRANT 后结束”，因为这无法恢复 migration ledger current，也会丢失 13:48 后本应由 forward migration 交付的行为。

### 2.3 Fix Resolution Trace active attempt projection

在 `loadRunAuthority` 中增加 scope/run-bound lateral lookup：

```sql
left join lateral (
  select attempt.attempt_id
  from run_attempts attempt
  where attempt.app_id = run.app_id
    and attempt.tenant_id = run.tenant_id
    and attempt.environment = run.environment
    and attempt.run_id = run.run_id
    and attempt.status = 'ACTIVE'
  order by attempt.attempt_no desc
  limit 1
) active_attempt on true
```

投影读取 `active_attempt.attempt_id`。局部唯一索引已保证同一 Run 最多一个 ACTIVE attempt；终态或队列未领取时自然得到 `null`。`runs.active_fence` 继续作为单调 fence 展示，不与 attempt identity 混为一列。

## 3. Test strategy

- Migration static test：checksum、baseline、owner/ACL、PUBLIC/backend deny、函数 definition postconditions。
- Renderer verify：10696 old bytes 与 10698 generated bytes 一致。
- Platform regression test：检查 authority SQL 使用 ACTIVE attempt lateral，并显式禁止 `run.active_attempt_id`。
- Existing Platform tests：Resolution Trace happy/empty/error paths。
- PostgreSQL validation：
  - `pnpm dev:migrate`；
  - ledger/current function owner/ACL 查询；
  - 目标工作空间前后计数对比；
  - PostgreSQL 日志确认不再出现三个已知错误。
- 若已登录浏览器会话可用，提交一个新问题并验证 201/Run 投影；否则记录该 UI 验证为需用户现场确认，不降低数据库和测试门禁。

## 4. Rollback and safety

- migration 不删表、不删行，只替换函数定义与调整精确 EXECUTE ACL。
- 应用前记录 ledger、目标 workspace 的 Conversation/Message/Run/Outbox 计数；应用后 exact compare。
- 如果 10698 事务内任一 postcondition 失败，整个 migration 自动回滚且不登记 ledger。
- TypeScript 查询修复可由本任务 Git commit 回退；不改写现有历史提交。
- 已成功登记的 forward migration 不通过删除 ledger 回滚；后续问题使用新的 repair migration。
