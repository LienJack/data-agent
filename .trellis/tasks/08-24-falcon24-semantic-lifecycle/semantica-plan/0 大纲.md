# Semantica 参考后的语义生命周期唯一方案

## 目标与边界

目标是在 Data Agent 内形成唯一的语义生产与消费闭环：`来源证据 → 候选 → 冲突/约束校验 → 人审 → 发布 → 召回 → 规则推理 → 上下文裁剪 → SQL/Python 分析 → Oracle → 反馈候选`。

PostgreSQL 中的 Published Semantic Release 是唯一逻辑权威。Neo4j、稀疏索引和向量索引只做可重建投影。模型只能提出候选、生成分析程序和解释证据，不能发布语义、扩大权限或覆盖确定性 Oracle。

最终不保留兼容层：运行时只有 `SemanticContextPackage`、`AnalysisProgram` 和一个解析入口。现有 `ResolvedContextPackage`、探索性 `ResolvedContextPackageV3`、旧 resolver、旧 `AnalysisPlan`、双读 adapter 和 dead tests 在同一次切换中删除。

## 采用、改造与拒绝

| 结论 | Semantica 模式 | Data Agent 处理 |
| --- | --- | --- |
| 采用 | 冲突检测、实体去重、双向血缘、时态快照、规则前向推理、RRF、能力问题 | 做成有版本、有证据、有回执的确定性模块 |
| 改造 | 图生成本体、SHACL、图向量混合召回 | 只生成 Candidate；校验需覆盖 Formula AST、粒度、Join、时间和权限；召回必须先权限过滤再扩图 |
| 拒绝 | 图存储成为事实权威、自动合并覆盖、LLM 本体直接发布、把模型 reasoning 当审计证据 | PostgreSQL 发布版本唯一权威；冲突阻止发布；只公开规则/证据路径，不记录模型 CoT |

Semantica 的源码还暴露了需要避免的实现问题：`GraphBuilder` 在冲突检测前写 GraphStore；`resolve_conflicts()` 的自动解决仅计数、不回写；能力问题可回答性只是关键词启发式；`ContextRetriever` 缺少强制依赖闭包和统一 token 裁剪。因此只借设计模式，不整体移植。

## 唯一目标架构

```text
Schema / Lineage / Glossary / Knowledge / Human / Model proposal
                          |
                  Semantic Factory
  identity -> conflict -> constraints -> competency cases -> review
                          |
           PostgreSQL Published Semantic Release
              |          |            |
        lexical/BM25   vector       Neo4j projection
              \          |            /
                 Semantic Context Compiler
 prefilter -> multi-route seeds -> typed graph closure -> Datalog closure
             -> mandatory preservation -> token-aware pruning -> receipt
                          |
                SemanticContextPackage
                          |
                    AnalysisProgram
            SQL evidence + DeepSeek Python sandbox
                          |
               deterministic Oracle / report
                          |
      misses, drift, conflicts and failures -> new Candidates
```

## 阶段路线

1. M1：唯一合同与权威切换边界。
2. M2：语义生产工厂与发布事务。
3. M3：多路召回与血缘图扩展。
4. M4：可解释逻辑推理与闭包裁剪。
5. M5：DeepSeek 生成 Python 的 Agent 分析路径。
6. M6：Falcon24 五题验收、反馈迭代与旧路径删除。

## 关键接口

- `SemanticAssertionCandidate`：来源、声明、时态、置信度、证据、冲突身份。
- `SemanticChangeSet`：候选集合、变更影响、校验结果、评审状态。
- `PublishedSemanticRelease`：唯一可消费的业务语义快照。
- `SemanticContextPackage`：授权后的实体、关系、公式、血缘、推理结论和召回回执。
- `AnalysisProgram`：SQL/Python/Oracle DAG，绑定固定上下文与数据证据。
- `SemanticRetrievalReceipt`：各路排名、图路径、推理规则、裁剪理由和降级原因。

## 总体验收

- PostgreSQL 权威断言通过；删除 Neo4j/向量索引后可从同一 Release 完整重建。
- 所有消费先完成 workspace、权限、发布状态、有效时间和冲突状态过滤。
- 公式、Join、血缘、时间、权限、质量依赖形成 mandatory closure，不能因 token 预算被静默裁掉。
- 每个推理结论可追溯到 premises、rule id、release id 和有效时间，不包含模型 CoT。
- Falcon24 五题均由固定 `deepseek-v4-flash` 生成 Python 并在无网络沙箱执行，独立 Oracle 5/5；冷/暖各三次、flake=0。
- 依赖扫描证明旧合同、旧 resolver、旧 planner、兼容 adapter 和双读引用为 0；生产只有一个入口。

## 假设

- Falcon24 数据库为 `falcon_db_24`；完整月边界按数据最大日期确定，不使用系统当前月猜测。
- 图扩展默认上限为 3 hop、80 nodes、160 edges；mandatory closure 超限时失败并要求澄清，不能返回缺失依赖的答案。
- 运行时推理只支持可终止、可解释的分层 Datalog/前向规则子集，不引入完整 OWL DL 推理器。
