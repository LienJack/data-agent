# M3 多路召回与血缘扩展

## 目标

让 Agent 高效率利用语义层：先找对种子，再沿类型化血缘补齐分析所需的完整语义子图。

---

## 实现步骤

1. 在任何检索前硬过滤 workspace、RBAC、Published、valid time、敏感级别和冲突状态。
2. 并行执行 exact alias/glossary、模糊/BM25、向量和图种子四路召回。
3. 用 RRF `k=60` 融合不同量纲排名，并保留每路贡献，不直接混加原始分数。
4. 从高置信种子按关系类型扩展：Formula、Join、Bind、Lineage、Time、Policy、Quality。
5. 对问题意图应用关系模板，例如趋势题强制补时间/指标公式，归因题补维度/分解路径，留存题补 cohort/time/customer 关系。
6. 输出 `SemanticRetrievalReceipt`，记录命中、扩展路径、降级、缺失和候选淘汰原因。

---

## 代码分析

### 结构职责

- Semantica `ContextRetriever` 证明 vector+graph+memory 组合与多跳扩展的可行性；`HybridSearch` 提供 RRF 实现。
- Data Agent 已有关系索引和 PostgreSQL fallback，但最终入口必须统一到 Semantic Context Compiler。

### 关键实现

- 图是导航索引，命中节点在装入上下文前必须回 PostgreSQL 校验 release/hash/permission。
- 图扩展采用 3 hop、80 nodes、160 edges 硬边界，并按关系类型设置 quota 和方向。

### 风险与坑点

- Semantica ContextRetriever 会吞掉部分向量/内存错误并返回空结果；Data Agent 必须在回执中显式标记 degraded route。
- 图度数高会把预算耗在邻居噪声上；必须先关系模板后 BFS，不能无类型全邻居扩展。

---

## 验收标准

- ACL、时间或未发布对象在四路召回和最终上下文中均不可见。
- exact、fuzzy、vector、graph 的 golden query 与同义改写召回率达到独立阈值，并记录 route contribution。
- 删除任一投影后 PostgreSQL 可重建，重建前后同一 query 的必需对象集合一致。
- 高度节点、循环图、索引陈旧和单路故障均有确定性、有界结果或明确失败。
