# 工作空间隔离、权限与模型计费

## Goal

把当前 Data Agent 从单一全局工作台演进为按项目/工作空间组织的多用户数据分析平台：用户进入一个项目或工作空间后，只能在该边界内使用已绑定的数据源、语义、对话分析与归因结果；平台同时提供基于角色的权限控制，以及由超级管理员管理的积分和模型计费能力。

## User Value

- 团队可以按项目或工作空间组织数据资产与分析活动，避免不同业务上下文互相污染。
- 一个工作空间可以绑定一个或多个数据源，并在同一隔离边界内进行语义建模、对话分析和归因分析。
- 语义资产可以通过 JSON 文件导入或导出，用于迁移、备份或跨环境协作。
- 管理员可以控制成员权限、模型配置和积分余额；普通用户可以清楚理解和追踪模型消费。

## Repository Evidence

- F1. PostgreSQL 已有以 `(app_id, tenant_id, environment, principal_id)` 为主键的 `memberships`，角色包含 `owner / analyst / viewer / demo`；`runs` 也以同一租户作用域保存并外键关联成员资格（`infra/supabase/apps/data-agent/migrations/20260725010100_app_data_agent_core.sql:208`、`:224`）。这为工作空间级数据库隔离提供了基础，但当前 `tenant_id` 尚无面向用户的工作空间实体和元数据。
- F2. 平台已有服务端签发并在事务内重验的 `AppCapability`，可限制 `OWNER / ANALYST / VIEWER` 的读写操作（`packages/platform/src/tenancy/postgres-authority.ts:54`、`:117`、`:193`）。当前角色是内部 capability 角色，不能直接等同于完整产品 RBAC。
- F3. Web 语义运行时仍从固定环境变量读取单个 `deployment / tenant / principal`，请求不能根据登录用户和所选工作空间动态解析 authority（`apps/web/src/lib/semantic-explorer-runtime.ts:122`、`apps/web/src/lib/semantic-candidate-runtime.ts:170`）。
- F4. 数据源连接、模型配置和 Q&A 对话当前分别保存于进程内 `Map`，没有持久化的工作空间键或用户键（`apps/web/src/lib/datasource-repository.ts:25`、`apps/web/src/lib/model-store.ts:18`、`apps/web/src/app/api/qa/conversations/route.ts:12`）。
- F5. Q&A 类型只记录单个 `dataSourceId`，发送分析请求时仍硬编码 `workspaceId = "default"`（`apps/web/src/lib/qa-types.ts:12`、`apps/web/src/lib/qa-store.ts:182`），尚不满足一个工作空间选择多个数据源的目标。
- F6. Web 包当前没有认证或会话依赖，也没有请求级认证中间件，因此用户登录、会话和超级管理员身份都是新增能力（`apps/web/package.json:13`）。
- F7. 模型契约已经支持经过验证的币种、输入/输出每百万 token 微单位价格，并以 `bigint` 做保守成本估算（`packages/contracts/src/providers/index.ts:68`、`packages/agent-runtime/src/models/router.ts:121`）。模型执行桥要求供应商返回完整的实际输入/输出 token 用量（`packages/agent-runtime/src/mastra/mastra-execution-bridge.ts:227`、`:553`）。计费可以复用这些契约，但当前没有用户积分账户、价格版本、调用账单或扣费账本。
- F8. 现有 `DataFoundry 平台模块` 任务明确把 RBAC 排除在范围外，因此本任务作为独立顶层架构规划，并需要定义与其数据源、Q&A、语义和模型模块的集成与迁移边界。

## Confirmed Requirements

### Project And Workspace

- R1. `项目` 与 `工作空间` 是同一个产品概念；系统规范、数据库和 API 统一使用 `workspace`，中文界面统一显示“工作空间”。
- R1.1. 用户进入业务功能前，可以选择工作空间。
- R2. 工作空间是数据源、语义、对话分析和归因分析的隔离边界。
- R3. 一个工作空间可以绑定一个或多个数据源。
- R3.1. 单次对话分析或归因分析运行必须从当前工作空间已绑定的数据源中选择且仅选择一个。
- R3.2. MVP 不支持单次运行跨数据源汇总或数据库级联邦查询；用户可以在不同对话/运行中选择不同数据源。
- R4. 工作空间之间的语义资产互相隔离。
- R5. 对话分析历史和结果按工作空间隔离。
- R6. 归因分析运行、历史和结果按工作空间隔离。
- R7. 语义资产支持以 JSON 文件导入和导出；导入不得绕过工作空间隔离。
- R7.1. 导出只包含当前工作空间的当前已发布语义版本及其可移植元数据，不包含凭证、成员、审核身份或其他工作空间标识。
- R7.2. 导入必须先校验 schema version、内容完整性、数据源绑定和目标工作空间权限，再创建目标空间内的语义草稿。
- R7.3. 导入草稿必须进入现有语义审核与发布流程，不能直接覆盖当前已发布版本；失败导入不得产生部分生效状态。
- R7.4. 导入向导必须要求用户将文件中的每个数据源引用显式映射到目标工作空间已有数据源；缺少可用目标时暂停导入，允许创建数据源后继续。
- R7.5. 系统不得从语义 JSON 自动创建数据源连接或凭证占位项。
- R7.6. 只有超级管理员可以创建、归档和恢复工作空间；工作空间管理员不得创建新的工作空间或改变工作空间生命周期。

### Users And Authorization

- R8. 系统提供用户管理能力。
- R8.1. 系统不开放用户自主注册；只有超级管理员可以创建、启用、停用和重置用户账号。
- R8.2. 超级管理员创建账号后，再将用户分配到一个或多个工作空间并指定工作空间角色。
- R8.3. 被停用用户的现有会话必须失效，且不得继续创建分析运行或访问工作空间数据。
- R9. 用户具有角色，角色决定其对项目或工作空间的操作权限。
- R10. 超级管理员拥有全部系统操作权限。
- R11. 只有超级管理员可以新增、修改、启用或停用模型配置。
- R12. 普通用户不得修改模型配置。
- R13. 用户账号是全局实体，可以加入多个工作空间，并在不同工作空间拥有不同角色。
- R13.1. MVP 使用预置角色，不提供自定义角色编辑器：
  - `SUPER_ADMIN`：全局角色，拥有全部系统操作权限，且是唯一可以管理模型配置、模型价格和用户积分的角色。
  - `WORKSPACE_ADMIN`：工作空间角色，管理该空间的成员、数据源和语义资产，并可使用分析能力；不能管理全局模型或积分。
  - `ANALYST`：工作空间角色，可使用获准数据源进行对话/归因分析，并按语义治理规则创建或编辑语义候选；不能管理成员、模型或积分。
  - `VIEWER`：工作空间角色，只能查看该空间内获准的资产与分析结果，不得创建运行或修改资产。
- R13.2. 同一用户在工作空间 A 的角色不得授予其访问工作空间 B 的权限。

### Credits And Model Billing

- R14. 普通用户使用系统时消耗积分。
- R15. 只有超级管理员可以为用户增加积分。
- R16. 积分价值固定为 100 积分 = 1 人民币。
- R17. 模型调用根据模型官方 API 价格扣除积分。
- R18. 系统除模型配置外，还必须保存模型价格及其生效信息，支持计费追溯。
- R19. 每次扣费必须能够关联到用户、工作空间、模型、实际用量和对应分析运行或对话。
- R19.1. 超级管理员调用模型不消耗积分，但必须生成与普通调用相同粒度的用量和人民币成本记录，并标记为 `SYSTEM_FUNDED`，用于工作空间成本归因和全局审计。
- R20. 积分账户归属于全局用户，不归属于工作空间；普通用户在其有权访问的所有工作空间中共享同一余额。
- R21. 每笔积分消费必须保留 `workspace_id`，用于按工作空间审计和统计，但不得形成独立的工作空间余额。
- R22. 普通用户发起计费模型调用前，系统按该次运行的最大授权 token 预算和适用价格冻结积分；可用余额不足时不得启动调用。
- R22.1. 只有当系统能够依据模型能力、请求预算、所有可能发生的计价维度和已生效价格计算出保守上限时，才允许普通用户发起调用；价格、汇率或计价维度缺失时必须失败关闭。
- R23. 模型调用终止后，系统按供应商返回的实际输入/输出 token 用量结算，扣除实际积分并释放未使用的冻结积分。
- R23.1. 对缓存 token、长上下文阶梯、工具调用等供应商实际返回且会产生费用的维度，适配器必须标准化并参与结算；MVP 不支持的计价形态不得被静默当作零费用。
- R23.2. 调用失败但供应商已产生可验证用量时仍按实际用量结算；无法确定是否产生费用时进入人工复核状态，不得直接释放全部冻结积分或重复调用。
- R24. 冻结、结算和释放必须在数据库事务中保持幂等；同一模型调用重试或重复回调不得重复扣费。
- R25. 并发调用不得使用户可用余额小于零；账本需要区分可用余额、冻结余额和已结算余额。
- R26. 系统定期从支持的模型供应商官方价格来源抓取价格，保存来源、抓取时间、原始证据摘要和标准化后的待审核价格版本。
- R27. 自动抓取的价格不得直接生效；只有超级管理员可以审核并激活新的价格版本。
- R28. 抓取失败、页面结构变化、币种不受支持或价格字段不完整时必须保留当前生效版本并告警，不能用零价格或不完整价格覆盖。
- R29. 每个模型价格版本至少记录 provider、model、币种、适用计价维度及阶梯、计价单位、官方来源、原始证据哈希、解析器版本、抓取时间、审核人和生效区间。
- R29.1. 非人民币官方价格必须使用版本化汇率换算为人民币成本；汇率由系统从配置的权威来源同步为候选，只有超级管理员确认后生效。
- R29.2. 每次结算必须同时冻结官方原币价格快照、汇率版本、人民币成本和最终积分，后续价格或汇率变化不得改变历史账单。
- R29.3. MVP 按官方 API 成本 1:1 扣费，不增加用户组倍率、渠道倍率或平台加价。
- R30. MVP 不接入在线支付、支付订单、支付回调、退款或发票；积分只能由超级管理员人工调增或调减。
- R31. 每次人工调账必须记录操作人、目标用户、变动积分、调整前后余额、原因、时间和幂等键；不得直接覆盖余额。
- R32. `100 积分 = 1 人民币` 在 MVP 中用于模型成本换算、余额展示和内部对账，不代表系统已提供人民币充值能力。
- R33. MVP 积分永久有效，不按时间自动失效；所有余额变化仍必须来自账本条目。

## Acceptance Criteria

- [x] AC1. 用户选择工作空间后，数据源、语义、对话分析和归因分析的列表及详情都只返回该工作空间的数据。
- [x] AC2. 同一用户在两个工作空间中的语义与分析历史互不可见；没有成员资格的用户不能通过直接请求访问目标工作空间。
- [x] AC3. 一个工作空间可以绑定多个数据源，分析运行只能使用该工作空间允许的数据源。
- [x] AC4. 从工作空间导出的语义 JSON 可以被验证并导入到目标工作空间，且导入过程保留审计记录并遵守目标空间权限。
- [x] AC5. 非超级管理员无法通过 UI 或 API 修改模型配置、价格记录或为用户增加积分。
- [x] AC6. 超级管理员可以查看用户并为指定用户增加积分，操作形成不可篡改的积分账本记录。
- [x] AC7. 模型调用完成后，系统按该次调用适用的价格快照和实际 token/用量计算费用，并生成可追溯的积分账本记录。
- [x] AC8. 余额不足时的产品行为必须明确且可测试，不允许产生不可解释的负余额。
- [x] AC9. 用户可以查看余额和自己的消费明细；超级管理员可以查看全局计费与调账审计记录。
- [x] AC10. 新项目以 clean install 和显式开发库重建完成 schema 切换；不承诺保留旧开发数据，
  但重建后的数据、语义、运行、对话和模型配置必须使用统一 workspace scope，不能静默串租户。
- [x] AC11. 服务端从登录会话解析 `principal_id`，从受保护路由解析 `workspace_id`，并在同一事务内重验账号状态、成员资格和权限版本；客户端自报角色或工作空间不能提升权限。
- [x] AC12. 用户停用或成员资格撤销后，已有会话和旧 capability 不能继续访问受保护数据；直接猜测其他工作空间对象 ID 返回稳定的无权限结果且不泄露对象是否存在。
- [x] AC13. 两个并发调用和重复供应商回调不能导致重复扣费或负可用余额；同一幂等键同载荷稳定重放，同键异载荷明确冲突。
- [x] AC14. 调用失败但已有实际用量时正确结算；无法判断费用时进入 `REVIEW_REQUIRED` 并保留相应冻结额，管理员可审计和处理。
- [x] AC15. 价格或汇率候选未经超级管理员批准不能生效；同步失败时继续使用上一个有效版本，没有完整有效价格链时普通用户调用失败关闭。
- [x] AC16. 修改或激活新价格、汇率后，旧账单中的原币价格、汇率、人民币成本和积分值保持不变且可重算。
- [x] AC17. 人工积分调账、价格审批、用户管理、工作空间生命周期和成员变更都写入同事务不可变审计记录，敏感凭证不进入日志、账单或导出文件。
- [x] AC18. 语义导入 schema 不兼容、内容哈希错误、数据源映射缺失或权限不足时不创建部分草稿；成功导入只产生待治理草稿。
- [x] AC19. 超级管理员模型调用生成 `SYSTEM_FUNDED` 成本记录但不改变其积分余额；普通用户可以查看自己的余额与账单但不能查看其他用户余额。
- [x] AC20. 归档工作空间拒绝新写入和新运行，但保留超级管理员可审计的历史数据；恢复后仍使用原成员与权限版本重新授权。

## Constraints

- 工作空间隔离必须由服务端和数据库边界共同保证，不能只依赖前端筛选。
- 金额计算使用精确数值或最小计费单位，不能使用浮点数直接累计。
- 历史账单必须绑定价格快照；后续修改模型价格不能改变既有扣费记录。
- API Key 等模型凭证继续作为秘密处理，不能出现在普通用户响应、日志或导出文件中。
- 规划已获批准并进入分阶段实施；Phase 0/1 已交付，Phase 2-7 仍按独立子任务推进。

## Out Of Scope

- 在线支付、支付渠道接入、退款与发票。
- 自定义角色编辑器和字段级权限。
- 跨工作空间联合查询或共享语义。
- 自动从模型供应商网站抓取价格并直接生效。

## Key Decisions

- D1. `项目 = 工作空间`，不建立项目与工作空间两级层级。`workspace_id` 是数据源、语义、对话、归因、运行和工作空间成员资格的统一业务隔离键；现有底层 `tenant_id` 在迁移设计中映射到 `workspace_id`，但不在产品界面暴露两套概念。
- D2. MVP 采用预置角色：全局 `SUPER_ADMIN`，以及工作空间级 `WORKSPACE_ADMIN / ANALYST / VIEWER`。用户是全局账号，可以加入多个工作空间并分别获得角色；首期不实现自定义角色编辑器。
- D3. 积分采用全局用户个人账户。普通用户跨工作空间共享余额；消费账单仍强制记录工作空间、运行/对话和模型归因。
- D4. 计费采用“冻结后结算”：调用前按最大授权预算冻结积分，余额不足失败关闭；调用终止后按实际 token 用量结算并释放差额。所有操作以模型调用的幂等键防止重复扣费。
- D5. 模型价格由系统定期从官方来源抓取为待审核版本，只有超级管理员确认后才能生效；历史账单永久绑定结算时的价格版本和价格快照。
- D6. MVP 不接真实支付。只有超级管理员可以通过账本调增或调减用户积分；100:1 仅作为人民币价值换算与内部对账标准。
- D7. MVP 采用封闭式账号体系：不开放自主注册，只有超级管理员可以创建和管理用户账号，并将其分配到工作空间。具体登录凭证和首次登录重置流程在技术设计中按安全默认值实现。
- D8. 一个工作空间可绑定多个数据源，但单次对话或归因运行只能绑定一个数据源。跨源汇总和联邦查询不属于 MVP。
- D9. 超级管理员模型调用不扣积分，但必须按实际用量和生效价格生成 `SYSTEM_FUNDED` 成本记录；管理员权限不能使外部模型成本从审计中消失。
- D10. 语义 JSON 只导出当前已发布版本；导入只创建草稿，完成校验后仍必须经过现有审核/发布流程，禁止直接覆盖线上语义。
- D11. MVP 积分永久有效，不实现过期批次、到期提醒或自动失效。
- D12. 语义导入要求将源数据源引用显式映射到目标工作空间已有数据源；缺少目标时暂停并允许创建后继续，禁止自动创建占位连接。
- D13. 非人民币官方价格使用自动同步、超级管理员确认的版本化汇率换算。每次账单绑定原币价格与汇率快照；MVP 不加价、不使用用户组或渠道倍率。
- D14. 只有超级管理员可以创建、归档和恢复工作空间；`WORKSPACE_ADMIN` 只管理其所在工作空间的成员和资产。
- D15. 身份认证使用成熟认证组件承接密码和会话；业务授权仍由 Data Agent 的 PostgreSQL Authority 以用户状态、工作空间成员资格和权限版本为权威，不使用客户端角色声明直接授权。
- D16. 项目尚无必须保留的生产数据，数据库演进优先 clean install；允许删除并重建开发数据，
  不建设旧数据 backfill、双写或在线升级链路。
